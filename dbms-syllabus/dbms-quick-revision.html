Three-Schema Architecture & Data Independence TOP PRIORITY 🔥
External, Conceptual, Internal Levels
Three-Schema Levels
External Level (User-specific views)↓ Conceptual Level (Complete logical structure)↓ Internal Level (How data is physically stored)
Physical Data Independence

Change physical storage (e.g. HDD → SSD) without changing logical schema. Applications remain unchanged.

Logical Data Independence

Change conceptual schema without affecting user views/applications. Harder to achieve than physical independence.

Keys in Relational Model TOP PRIORITY 🔥🔥
Super Key, Candidate Key, Primary Key, Foreign Key, Prime vs Non-Prime
Super Key (SK)

Any attribute/set of attributes that uniquely identifies a tuple. e.g. {ID}, {Email}, {ID, Name}.

Candidate Key (CK) ⭐

Minimal super key with no unnecessary attributes (e.g. ID, Email).

Primary Key (PK) ⭐

Candidate key selected to uniquely identify tuples. Unique and NOT NULL. Exactly 1 per table.

Alternate Key (AK)

Candidate keys not selected as primary key.

Foreign Key (FK) ⭐

Attribute referring to key of another table. Maintains referential integrity.

Composite Key & Unique Key

Composite: Key with multiple attributes. Unique Key: Ensures uniqueness; allows NULL (per DBMS).

Prime vs Non-Prime Attributes
  • Prime Attribute: Attribute belonging to at least one Candidate Key.
  • Non-prime Attribute: Doesn't belong to any Candidate Key.

Functional Dependency (FD) ⭐⭐⭐
A → B, Trivial, Non-Trivial, Completely Non-Trivial
If A → B, then value of A uniquely determines B. (Example: RollNo → Name).
  • Trivial FD: If B ⊆ A, then A → B. (Example: {ID, Name} → Name).
  • Non-Trivial FD: B is not a subset of A. (Example: ID → Name).
  • Completely Non-Trivial: A and B have no common attributes.

Pseudotransitivity (Derived)If X → Y and WY → Z, then WX → Z

Attribute Closure (X+)
Finding Candidate Keys & Super Keys
Closure X+ = all attributes functionally determined by X. Useful for finding candidate keys, super keys, and FD implications.
If: R(A,B,C,D) with FDs: A → B, B → C, C → D Then: A+ = {A, B, C, D} Therefore, A is a Candidate Key.

21
First Normal Form — 1NF
Atomic values only, no multi-valued/repeating fields
🔑 1NF Rule
1NF = No multi-valued / repeating fields (Atomic values only).
✘ Not in 1NF

Ravi | Phones: 111, 222 (Multiple values in single cell)

✓ In 1NF

Ravi | Phone: 111
Ravi | Phone: 222 (Atomic entries)

22
Second Normal Form — 2NF
Must be in 1NF + No Partial Dependency
🔑 2NF Rule
2NF removes Partial Dependency. (No non-prime attribute should depend on a proper subset of a composite candidate key).
Violation Example with Candidate Key (StudentID, CourseID): (StudentID, CourseID) → Grade StudentID → StudentName [Violates 2NF: StudentName depends only on part of CK] CourseID → CourseName [Violates 2NF: CourseName depends only on part of CK]
23
Third Normal Form — 3NF
Must be in 2NF + Remove Transitive Dependency
🔑 3NF Rule
3NF removes Transitive Dependency.
Formally, for every non-trivial FD X → A: X is a Superkey OR A is a Prime attribute.
Transitive Dependency Example: EmpID → DeptID, and DeptID → DeptName Therefore: EmpID → DeptName indirectly. Split into: Employee(EmpID, DeptID) and Department(DeptID, DeptName).
24
BCNF (Boyce-Codd Normal Form)
Stronger than 3NF — Determinant must be a Super Key
For every non-trivial FD X → Y, X must be a Super Key.
⭐ 3NF vs BCNF Distinction
3NF allows a non-superkey determinant when RHS is prime; BCNF doesn't.
Therefore: BCNF ⊆ 3NF (Every BCNF relation satisfies 3NF, but not vice versa).
25
Fourth Normal Form — 4NF
Must be in BCNF + Eliminate Multivalued Dependencies (MVD)
4NF = No non-trivial MVD (A ↠ B) unless the determinant is a superkey.
26
Fifth Normal Form (5NF) & Normalization Ladder ⭐⭐
Join Dependency (PJNF) & Sequence Summary
5NF (Project-Join Normal Form): Deals with Join Dependency. Relation should not be decomposable further into smaller relations without losing information, except decompositions implied by candidate keys.
The Normal Form Ladder — Memorize This Sequence! 🔥
LevelCondition
1NFAtomic values (no multi-valued attributes)
2NFNo Partial Dependency
3NFNo Transitive Dependency (X is Super Key OR A is prime)
BCNFEvery determinant is a Super Key
4NFNo problematic Multivalued Dependency (MVD)
5NFNo problematic Join Dependency (JD)

Lossless Join & Dependency Preservation
Lossless Decomposition (Preferred)

Original relation can be reconstructed exactly using JOIN. No spurious/missing tuples.

Lossy Decomposition (Bad)

Joining decomposed tables creates missing or spurious false information.

Lossless + Dependency Preserving (All original FDs can be checked without joining).

31
Transaction Schedules
Serial vs Concurrent / Non-Serial Schedules
Serial Schedule

Transactions execute one after another (T1 → T2 → T3). No interleaving. Always consistent, but poor resource utilization.

Concurrent / Non-Serial Schedule

Operations of transactions interleave. Better throughput/CPU utilization, but introduces potential concurrency problems.

32
Serializability & Conflict Serializability ⭐⭐⭐
Conflicting operations & Precedence Graph test
A schedule is serializable if its effect is equivalent to some serial schedule.
Operations conflict when: Different transactions + Same data item + At least one WRITE (R-W, W-R, W-W). (R-R is not a conflict).
🔑 Precedence Graph Test
Acyclic Precedence Graph → Conflict Serializable ✓
Cycle in Precedence Graph → Not Conflict Serializable ✘
33
Concurrency Problems
Lost Update, Dirty Read, Non-Repeatable Read, Phantom Read
Lost Update

One transaction overwrites another transaction's uncommitted update.

Dirty Read / Temporary Update

Transaction reads data written by uncommitted transaction that later aborts.

Non-Repeatable Read

Same row read twice gives different values (another transaction updated it).

Phantom Read

Same query returns a different set of rows (another transaction inserted/deleted rows).

🧠 Quick Difference
Non-repeatable → existing row changes  |  Phantom → result-set rows appear/disappear

Locks (Shared vs Exclusive)
Read (S) vs Write (X) locks and compatibility
  • Shared Lock (S): Used for READ. Multiple transactions can hold S-locks simultaneously.
  • Exclusive Lock (X): Used for WRITE. Only one transaction gets exclusive access.
Lock Compatibility Matrix

36
Two-Phase Locking — 2PL
Growing Phase, Lock Point, Shrinking Phase, Strict 2PL
Acquire Locks (Growing)→ LOCK POINT→ Release Locks (Shrinking)
  • Growing Phase: Locks can be acquired, not released.
  • Shrinking Phase: Locks can be released, not acquired.
  • 2PL ensures conflict serializability.
  • Strict 2PL: Exclusive/write locks are retained until commit/abort (prevents cascading rollback).
37
Deadlock & Wait-for Graph
Deadlock conditions, Wait-for Graph cycle detection
Example: T1 holds A → waits B; T2 holds B → waits A. Neither can continue.
  • Solutions: Prevention (Wait-Die, Wound-Wait), Avoidance, Detection & recovery, Timeout.
  • Wait-for Graph: A cycle indicates deadlock in single-instance resource lock systems.
38
Recoverability & Schedule Safety
Recoverable, Cascading Rollback, Cascadeless, Strict Schedule
  • Recoverable Schedule: If T2 reads data written by T1, Commit(T1) must occur before Commit(T2).
  • Cascading Rollback: One failed transaction causes dependent transactions to roll back.
  • Cascadeless Schedule: Transactions only read committed values.
  • Strict Schedule: No transaction can read or write an item written by an uncommitted transaction.
🔑 Safety Implication
Strict ⇒ Cascadeless ⇒ Recoverable
39
Recovery, Log-Based Recovery & WAL
Write-Ahead Logging, Deferred Update, Immediate Update, Checkpoint
  • Log-Based Recovery: Log records store transaction changes.
  • Write-Ahead Logging (WAL): Relevant log information is written to stable storage before corresponding database changes are written.
  • Deferred Update: Changes applied after commit (typically associated with REDO).
  • Immediate Update: Changes may reach database before commit (may require UNDO + REDO).
  • Checkpoint: Creates a recovery reference point, reducing recovery work.

Data Warehouse & Related Concepts

RAID Levels

RAID 0 & RAID 1

RAID 0: Striping — performance, no fault tolerance.
RAID 1: Mirroring — fault tolerance via duplication.

RAID 5 & RAID 10

RAID 5: Striping with distributed parity — balances performance & fault tolerance.

47
Distributed Databases & NoSQL
Fragmentation, Replication, CAP Theorem, BASE
  • Distributed Database: Data stored across multiple physical locations, appears as a single database to users.
  • Fragmentation: Splitting a relation (horizontal/vertical/mixed) across sites.
  • Replication: Copies of data maintained at multiple sites for availability.
  • CAP Theorem: A distributed system can guarantee at most 2 of Consistency, Availability, Partition tolerance at the same time.
  • NoSQL types: Key-Value, Document, Column-family, Graph — used when strict relational schema/ACID isn't the priority.
  • BASE (contrast with ACID): Basically Available, Soft state, Eventually consistent.

SQL Constraints & Referential Actions ⭐⭐

FOREIGN KEY (dept_id) REFERENCES Department(dept_id) ON DELETE CASCADE ON UPDATE CASCADE

Joins in SQL ⭐⭐⭐
INNER, LEFT, RIGHT, FULL OUTER, CROSS, SELF JOIN
Join TypeDescription & Behavior
INNER JOINOnly matching records (Intersection).
LEFT JOINAll rows from left table + matching right rows. Unmatched right → NULL.
RIGHT JOINAll rows from right table + matching left rows. Unmatched left → NULL.
FULL OUTER JOINAll rows from both tables, matched where possible.
CROSS JOINCartesian product (A = 5 rows, B = 4 rows → 20 rows).
SELF JOINTable joined with itself (e.g. Employee → Manager).
71
Natural Join
Implicit join on common column names
Automatically joins based on same-named compatible columns. Potentially risky because schema changes can alter join behavior.

= operator vs comparison operators
Equi Join

Theta Join

73
Subqueries ⭐⭐
Single-row, Multi-row, Nested subqueries
Query inside another query.
SELECT name FROM Employee WHERE salary > ( SELECT AVG(salary) FROM Employee );
  • Types: Single-row, Multi-row, Nested, Correlated.
74
Correlated Subquery
Subquery depending on outer query row evaluation
Depends on outer query; conceptually evaluated once for each outer row.
-- Find employees earning above their department average: SELECT e1.name FROM Employee e1 WHERE salary > ( SELECT AVG(e2.salary) FROM Employee e2 WHERE e2.dept_id = e1.dept_id );
75
EXISTS and NOT EXISTS
Checking for presence/absence of subquery rows
WHERE EXISTS ( SELECT 1 FROM ... )

Checks whether subquery returns at least one row. NOT EXISTS checks absence.

76
ANY and ALL Operators
Multi-row comparison operators
  • ANY: Condition must be true for at least one returned value. (salary > ANY (...)).
  • ALL: Condition must be true for every returned value. (salary > ALL (...)).
77
Set Operations (UNION, INTERSECT, EXCEPT/MINUS)
UNION vs UNION ALL and compatibility rules
  • UNION: Combines results and removes duplicates.
  • UNION ALL: Keeps duplicates (faster, no sorting needed).
  • INTERSECT: Returns common rows.
  • EXCEPT / MINUS: Returns rows in first query but not second (Oracle uses MINUS, standard SQL uses EXCEPT).
🔑 Set Operation Rule
Number and compatible data types of columns must match between both queries.
78
Window Functions ⭐⭐
ROW_NUMBER, RANK, DENSE_RANK, PARTITION BY
SELECT name, dept_id, salary, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk FROM Employee;
FunctionBehavior on Ties
ROW_NUMBER()Unique sequential number per row (1, 2, 3, 4)
RANK()Same rank for ties, skips next rank (1, 2, 2, 4)
DENSE_RANK()Same rank for ties, no gaps in next rank (1, 2, 2, 3)

PARTITION BY: Divides result set into groups without collapsing rows.

79
Views & Updatable Views
Virtual tables based on SELECT queries
CREATE VIEW HighEarners AS SELECT name, salary, dept_id FROM Employee WHERE salary > 70000;
  • Advantages: Simplifies complex queries, security layer, logical data independence.
  • Updatable views: Simple views (single table, no aggregates/GROUP BY/DISTINCT) are updatable.

Index Creation (SQL Syntax)
CREATE INDEX and DROP INDEX
CREATE INDEX idx_salary ON Employee(salary); -- To remove: DROP INDEX idx_salary;
81
Stored Procedures, Functions, Triggers, Cursors
Database programming objects
  • Stored Procedure: Precompiled set of SQL statements stored in DB, callable by name.
  • Function: Must return a value; usable inside SQL expressions.
  • Trigger: Automatically executed in response to an event (INSERT/UPDATE/DELETE).
  • Cursor: Database object used to retrieve/process query result rows one at a time.

TCL Commands (Transaction Control)
COMMIT, ROLLBACK, SAVEPOINT, START TRANSACTION
COMMIT; -- Saves changes permanently ROLLBACK; -- Undoes uncommitted changes SAVEPOINT sp1; -- Sets checkpoint ROLLBACK TO sp1; -- Rolls back to checkpoint

DELETE vs TRUNCATE vs DROP ⭐⭐⭐

🧠 Quick Memory Trick
DELETE → removes rows, DML, conditional, slower.
TRUNCATE → removes all rows fast, DDL, resets identity.
DROP → removes the whole table (structure + data).
