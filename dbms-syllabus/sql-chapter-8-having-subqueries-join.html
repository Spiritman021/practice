📊 Part A: HAVING Clause & Nested Query — Step by Step

This section builds directly on Chapter 7's GROUP BY. We add a HAVING filter to find departments with fewer than 2 employees, then extend it with a nested subquery to find the actual employee names working in those departments.

❓ Problem — Step 1: Find Departments With < 2 Employees

Goal: Print the department names where the number of employees is less than 2.

💡 Why Not WHERE?
WHERE filters individual rows before grouping. It has no concept of "count per group." To filter on an aggregate result (like COUNT), you must use HAVING — which runs after GROUP BY, at the group level.
Step 1 — Find low-count departments
SELECT   department
FROM     employee
GROUP BY department
HAVING   COUNT(*) < 2;

-- After GROUP BY:  HR(2), Marketing(2), IT(1)
-- HAVING count < 2: Only IT passes (count=1)
-- Output: IT

❓ Problem — Step 2: Find Employee Names in Those Departments

Now extend the query: print the names of employees who work in a department where the employee count is less than 2.

The inner query gives us the department name (IT). We use that as input to the outer query to fetch employee names.

Step 2 — Full Nested Query
SELECT   ename
FROM     employee
WHERE    department IN (
             SELECT   department
             FROM     employee
             GROUP BY department
             HAVING   COUNT(*) < 2
         );

-- Inner query executes first → Output: {IT}
-- Outer query: WHERE department IN ('IT')
-- Checks each row: HR∈{IT}? No · Marketing∈{IT}? No · IT∈{IT}? Yes
-- Final output: Varun

📌 WHERE vs HAVING — Final Summary
WHERE — Applied on rows, before grouping. Cannot use COUNT/SUM/AVG.
HAVING — Applied on groups, after GROUP BY. Must use aggregate functions.
WHERE + GROUP BY + HAVING together: WHERE filters rows first → GROUP BY groups them → HAVING filters those groups.

🪆 Part B: Nested Subquery (Simple Subquery)

A nested subquery (also called a simple subquery or regular subquery) is a query inside another query. The inner query runs completely first, returns a result, and then the outer query uses that result. This is a bottom-up approach.

⚙️ How It Works

📌 Bottom-Up Approach
Step 1: Inner query executes once and produces a result set.
Step 2: Outer query uses that result set (via IN) to filter its rows.

Inner query does NOT know about the outer query. They are independent.
Method 1 — Nested Subquery
SELECT  *
FROM    emp
WHERE   E_id IN (
            SELECT E_id   ← Inner query — runs FIRST, ONCE
            FROM   dept    ← Gets E_id from dept table
        );

-- Inner query executes: SELECT E_id FROM dept → {1, 2, 3}
-- Outer query: SELECT * FROM emp WHERE E_id IN (1, 2, 3)
-- Compare each emp row's E_id against {1,2,3}
-- Output: rows for 1(A), 2(B), 3(C)

🔄 Part C: Correlated Subquery

In a correlated subquery, the inner query references a column from the outer query. This means the inner query cannot run independently — it must be re-evaluated for each row of the outer query. This is a top-down approach.

⚙️ How It Works

📌 Top-Down Approach
Step 1: Pick the first row from the outer table (emp).
Step 2: Run the inner query using that row's value.
Step 3: If EXISTS returns TRUE → include outer row in result.
Step 4: Repeat for every row in the outer table.

Inner query runs once per outer row. Total executions = number of rows in emp.
Method 2 — Correlated Subquery
SELECT  *
FROM    emp e
WHERE   EXISTS (
            SELECT 1              ← Inner query — runs per OUTER ROW
            FROM   dept d
            WHERE  d.E_id = e.E_id  ← References outer table 'e'!
        );

-- For each row in emp, inner query checks: does dept have this E_id?
-- EXISTS returns TRUE if inner query returns at least 1 row
-- Row included if EXISTS = TRUE

🔗 Part D: JOIN (Cross Product + Condition)

A JOIN combines both tables into one temporary large table (cross product) and then filters using a condition. Unlike correlated subquery, it processes both tables together at once.

⚙️ How It Works

📌 Cross Product → Filter
Step 1: Create a temporary buffer table = cross product of emp × dept (m×n rows).
Step 2: Apply the join condition (emp.E_id = dept.E_id) on this buffer.
Step 3: Matching rows are the final result.

Both tables are loaded once into a big buffer. All comparisons happen on that single buffer — like moving everyone into one big room.
Method 3 — JOIN
SELECT  e.*
FROM    emp e, dept d            ← Both tables loaded (cross product)
WHERE   e.E_id = d.E_id;        ← Filter condition on combined table

-- Modern syntax (equivalent):
SELECT  e.*
FROM    emp e
INNER JOIN dept d ON e.E_id = d.E_id;

-- Cross product first: 5 × 3 = 15 temporary rows in buffer
-- Then filter where emp.E_id = dept.E_id
-- Matching: (1,A)·D1, (2,B)·D2, (3,C)·D3
-- Output: rows for A, B, C

📦 Cross Product Visualization (5×3 = 15 rows)

🏠 The "One Big Room" Analogy
Correlated: Move person 1 from room A to room B to compare with all 3 people there. Bring them back. Move person 2. Repeat. This is slow due to repeated I/O.

JOIN: Move ALL 5 people from room A and ALL 3 from room B into ONE big room. Do all 15 comparisons right there. Faster, but needs a bigger room (more space/memory).

⚡ Final Comparison — All Three Methods

🪆 Nested Subquery
Bottom-Up

Inner query runs once. Result handed to outer query as a static list. Uses IN (for multiple values) or = (for single value).

✅ Best when: Inner query result is small and independent of outer
🔄 Correlated Subquery
Top-Down

Inner query runs once per outer row. References outer table inside inner query. Uses EXISTS. m×n comparisons total.

✅ Best when: Inner result depends on current outer row
🔗 JOIN
Cross Product + Filter

Both tables combined into a buffer (m×n rows). Condition applied on buffer. Uses more space but faster in practice due to single I/O pass.

✅ Best when: Performance matters; space is not constrained

⚠️ Space is Cheap, Time is Expensive
In modern systems, storage is cheap but query time directly affects user experience. That's why JOIN is often preferred over correlated subquery for large datasets — even though it uses more memory, it avoids repeated I/O operations by processing everything in one batch.

🎯 Interview & Exam — Key Q&A

Q1: Why can't you use WHERE COUNT(*) < 2? Why use HAVING?
👉 WHERE runs before GROUP BY (step 3) and cannot use aggregate functions. COUNT(*) is an aggregate result that exists only after grouping. HAVING runs after GROUP BY (step 5) and is the correct clause for group-level conditions.

Q2: What is a nested subquery? How is execution order different from correlated?
👉 Nested: inner query runs once independently, gives a result, outer uses it (bottom-up). Correlated: inner runs once per outer row and references the outer query (top-down). Nested is more efficient when the inner result is reusable.

Q3: When do you use IN vs = in a subquery?
👉 Use = when inner query returns exactly one value. Use IN when inner query returns multiple values (a set). Using = with a multi-row result throws an error.

Q4: What is a correlated subquery? What keyword does it use?
👉 A subquery that references columns from the outer query. The inner query cannot run independently — it re-executes for each outer row. It typically uses EXISTS (returns true/false) rather than IN.

Q5: How does JOIN differ from a nested subquery?
👉 JOIN performs a cross product of both tables into a temporary buffer (m×n rows) and then applies the condition in one pass. Nested subquery runs the inner query once and uses the result list. JOIN uses more space but avoids repeated I/O.

Q6: What is the number of comparisons in a correlated subquery vs JOIN (m rows in emp, n rows in dept)?
👉 Both do m×n comparisons total. But correlated does it in m separate inner query executions (high I/O), while JOIN does it in one batch on the buffer (lower I/O, faster).

Q7: What does EXISTS return?
👉 EXISTS returns TRUE if the inner query returns at least one row, and FALSE if it returns no rows. It's used in correlated subqueries to check whether a matching record exists in the related table.

Q8: Do nested subquery, correlated, and JOIN give the same result?
👉 Yes — for the same logical query (find employees working in any department), all three methods return identical results. The difference is only in how they work internally (performance and readability).

Q9: Why is JOIN generally faster than correlated subquery for large tables?
👉 Correlated subquery repeatedly reads the inner table (m times), causing high I/O. JOIN reads both tables once, creates a buffer, and processes all comparisons in one batch — much more I/O-efficient.

Q10: What happens to employees with no department (4·D and 5·E) in all 3 methods?
👉 All 3 methods correctly exclude them. Nested: 4 and 5 are not IN {1,2,3}. Correlated: EXISTS returns false (no match in dept). JOIN: no matching dept row, so they don't appear after the condition filter.
