Views in SQL

One of the most placement-critical SQL topics. A view is far more than just a "virtual table" — understand how stored queries, base-table propagation, read-only vs updatable vs materialized views, and role-based access control all connect together.

👁️ Virtual Table 🗄️ Stored Query 🔒 Read-Only View ✏️ Updatable View 📸 Materialized View 🔐 Security & Access Control

👁️ What is a View?

In a placement or interview, the first answer to "What is a View?" is — virtual table. But that is just the starting point. A complete answer covers why it's virtual, how it's stored, and how changes propagate.

📘 Formal Definition
A View is a named, stored SQL query whose result looks and behaves like a table but has no physical storage of its own. It is created from one or more base tables (or other views) using a SELECT statement. The view's definition (the query) is compiled and stored; the result set is generated on demand when you query the view.

🧠 The "Stored Query" Mental Model

Think of a view like a saved camera angle. The actual scene (data) lives in the base table. The camera just frames a particular portion of it. Every time you look through the camera (query the view), you see the live scene at that moment — no separate copy is stored.

CREATE VIEW V1 AS SELECT id, name FROM student WHERE city = 'Delhi';
⬇ SQL engine compiles the query, stores definition
View V1 definition stored in Data Dictionary (not the result rows)
⬇ When user queries
SELECT * FROM V1;
⬇ Engine executes the stored query on the live base table
Result set returned as if it were a real table — but nothing is stored!

💡 Parent → Child Analogy
The base table is the parent; the view is the child. Whatever you change in the parent (base table) is always visible in the child (view). Whether the child (view) can push changes back to the parent depends on whether it's an updatable view.

🗂️ Types of Views

🔒
Read-Only View
Users can only SELECT (read) from this view. INSERT, UPDATE, and DELETE operations are disabled/blocked. The base table is fully protected from changes through this view. Created using WITH READ ONLY in Oracle.
✅ Most Common for Security
✏️
Updatable View
Users can perform SELECT, INSERT, UPDATE, DELETE on this view. Changes made through the view are propagated back to the base table. Used when controlled write access through a view is needed.
⚠️ Use with caution — writes to base table
📸
Materialized View
Unlike a normal view that stores only the query, a materialized view stores the actual result set physically (a snapshot). Used heavily in data warehousing and data mining. It does take up disk space but enables much faster reads. The snapshot can be refreshed periodically or on-demand.
🏭 Used in Data Warehouse / DW

📸 Materialized View — Deep Dive

A materialized view is like keeping a local cache copy of remote server data. In a client-server architecture, your main data sits on a remote server. Instead of querying the server every single time, you take a snapshot and store it locally — this is exactly what a materialized view does inside the database engine.

📝 CREATE VIEW — Syntax & Examples

Oracle SQL — Basic Syntax
-- Basic syntax
CREATE [OR REPLACE] VIEW view_name AS
  SELECT col1, col2, ...
  FROM table_name
  [WHERE condition]
  [WITH READ ONLY];        -- optional: makes it read-only
Oracle SQL — Example 1: Simple View
-- Base table: student(id, name, father_name, city, marks)
-- Create a view showing only id and name
CREATE VIEW V1 AS
  SELECT id, name
  FROM student;

-- Query the view just like a table
SELECT * FROM V1;
-- Returns: id and name of all students (from base table, live)
Oracle SQL — Example 2: Filtered View (WHERE clause)
-- View of only Delhi students (restricts rows)
CREATE VIEW V_Delhi AS
  SELECT id, name, city
  FROM student
  WHERE city = 'Delhi';
Oracle SQL — Example 3: Read-Only View
-- Create a read-only view (no INSERT/UPDATE/DELETE allowed)
CREATE VIEW V_Faculty_Public AS
  SELECT faculty_name, course, qualification
  FROM faculty
  WITH READ ONLY;

-- Attempting DML on this view will throw an error:
-- ORA-42399: cannot perform a DML operation on a read-only view
Oracle SQL — Example 4: View from Multiple Tables (JOIN)
-- View combining data from 2 tables
CREATE VIEW V_Emp_Dept AS
  SELECT e.emp_id, e.name, d.dept_name
  FROM employees e
  JOIN departments d ON e.dept_id = d.dept_id;
Oracle SQL — OR REPLACE and DROP VIEW
-- Replace/modify an existing view without dropping first
CREATE OR REPLACE VIEW V1 AS
  SELECT id, name, city FROM student;

-- Delete a view (only removes the view definition, NOT the base table)
DROP VIEW V1;

⚠️ DML Rules on Views

⚠️ DDL is NOT allowed on Views
You cannot run ALTER TABLE or other DDL commands on a view — views are not physical tables. You can only run:

SELECT — always allowed on all views
INSERT / UPDATE / DELETE — only on updatable views (not read-only)

To modify a view's definition: use CREATE OR REPLACE VIEW.

✅ Advantages of Views

🔐
Restrict Data Access (Security)
Don't expose the full base table. Show only the columns/rows a user needs. Expose a 4-column view from a 20-column table — the user doesn't even know the other columns exist.
🧩
Simplify Complex Queries
Instead of writing a complex multi-table JOIN repeatedly, create a view once. Then just SELECT * FROM that_view. Example: separate 2019, 2020, 2021 sales data into 3 simple views.
🔗
Data Independence
If the base table structure changes (columns added/renamed), views can absorb the change — users working with the view are unaffected as long as their columns still exist.
👥
Role-Based Access (Different Views)
Student sees: name, marks. Faculty sees: name, marks, grade. HOD sees everything. Each user role gets a tailored view — all from the same underlying base table.

🏫 University System Real-World Example

✅ Real-World Application — University DBMS
Base Table (faculty): faculty_id, name, address, phone, qualification, salary, bank_account, contract_details, emergency_contact, leaves_taken…

View for Students: SELECT name, course, qualification FROM faculty — Students see only this.

🎯 Interview & Exam — Key Q&A

Q1: What is a View in SQL? Why is it called a virtual table?
👉 A view is a stored SQL query whose result looks like a table but has no physical data storage. It's called virtual because unlike a real table, it doesn't occupy disk space — only the query definition is stored. The result is generated dynamically when the view is queried.

Q2: What is the difference between a base table and a view?
👉 A base table physically stores data on disk. A view stores only a SELECT query. The view generates its result by executing that query on the live base table each time it's queried.

Q3: If you update data in the base table, does the view reflect the change?
👉 Yes, always and automatically. Since the view executes the SELECT query on the live base table each time, any change in the base table (INSERT/UPDATE/DELETE) is immediately visible in the view.

Q4: What is a Read-Only view? How do you create one in Oracle?
👉 A read-only view blocks all DML operations (INSERT, UPDATE, DELETE). Users can only SELECT from it. Created using: CREATE VIEW v_name AS SELECT ... WITH READ ONLY;

Q5: What is an Updatable View?
👉 An updatable view allows INSERT, UPDATE, and DELETE operations. Changes made through the view are propagated back to the base table. Not all views can be updatable — complex views with JOINs, GROUP BY, DISTINCT may restrict this.

Q6: What is a Materialized View? How is it different from a normal view?
👉 A materialized view physically stores the result set (snapshot) unlike a normal view that only stores the query. It takes disk space but is faster to query. It can become stale and needs periodic refresh. Used primarily in data warehousing.

Q7: Can you apply DDL commands like ALTER TABLE on a view?
👉 No. DDL commands (ALTER, DROP TABLE etc.) cannot be applied on a view. To modify a view's definition, use CREATE OR REPLACE VIEW. To delete a view, use DROP VIEW.

Q8: Can a view be created from multiple tables?
👉 Yes. A view can JOIN multiple tables and present columns from all of them as a single virtual table. This is one of the main use cases — simplifying complex multi-table queries.

Q9: What are the security advantages of views?
👉 Views allow you to expose only selected columns/rows to users without giving them access to the full base table. For example, students can see a faculty view with name and course only, while the base table may contain salary, bank details, and personal information.

Q10: If you DELETE a row through an updatable view, what happens to the base table?
👉 The row is deleted from the base table. Any DML operation on an updatable view directly affects the underlying base table. This is why read-only views are preferred when write access should be controlled.
