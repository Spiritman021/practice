1NF, 2NF, 3NF & BCNF

The core of database normalization. Learn each normal form step-by-step, with real examples, diagrams, and GATE PYQs — all in one tabbed page.

1NF — Atomic Values 2NF — No Partial Dep 3NF — No Transitive Dep BCNF — LHS = CK always
Normal Form Hierarchy — Each NF is a strict subset of the previous. BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF

🔵 First Normal Form (1NF)

Proposed by E.F. Codd (Father of DBMS). 1NF is the most basic rule every table must follow.

RULE OF 1NF
A table is in 1NF if and only if:
Every attribute contains ONLY ATOMIC (indivisible) values.
→ No multivalued attributes allowed in a single cell.
💡 What is Atomic?
Atomic means each cell has exactly ONE value — you cannot store multiple values separated by commas, spaces, or any delimiter in a single column. Each row-column combination must hold a single, indivisible value.

❌ Table NOT in 1NF

Consider the following Student table — Course column has multiple values for one student:

Roll_NoNameCourse
1SaiC, C++
2HarshJava
3OmkarC, DBMS
❌ Why is this NOT 1NF?
Sai has C, C++ in Course column (2 values) and Omkar has C, DBMS (2 values). Even one attribute with multiple values in any row makes the table violate 1NF.

✅ 3 Methods to Convert to 1NF

📋 Method 1 — Separate Rows (Composite PK)
Split each multi-valued row into separate rows. One row per course per student.
Roll_No 🔑NameCourse 🔑
1SaiC
1SaiC++
2HarshJava
3OmkarC
3OmkarDBMS
🔑 Primary Key?
Roll_No alone repeats (e.g. Roll_No=1 appears twice). Course alone repeats too. But {Roll_No, Course} together is unique → Composite Primary Key = (Roll_No, Course)
📋 Method 2 — Multiple Columns (Course1, Course2)
Create separate columns for each course slot. Max courses = 2 here, so make Course1 and Course2.
Roll_No 🔑NameCourse1Course2
1SaiCC++
2HarshJavaNULL
3OmkarCDBMS
⚠️ Problem with Method 2
Primary Key = Roll_No (simple PK — works!). But if a student enrolls in 10 courses, you need 10 columns. Students with fewer courses will have many NULL values. Too many NULLs = wasteful and problematic design.
📋 Method 3 — Decompose into 2 Tables ⭐ BEST APPROACH
Split into a Base Table (students) and a Referencing Table (enrollments).

🎯 GATE-Style PYQs — 1NF

Q1. A table has attribute Course with values {C, C++} for a student. The table is:
👉 NOT in 1NF — multivalued attribute violates atomicity.
Q2. What is the primary key when converting 1NF using Method 1 (separate rows) for a Student(Roll_No, Name, Course) table?
👉 (Roll_No, Course) — Composite Primary Key
Q3. Which normal form deals with eliminating multivalued attributes?
👉 First Normal Form (1NF)

🟢 Second Normal Form (2NF)

RULES OF 2NF (Both must be satisfied)
Rule 1: Table must be in 1NF
Rule 2: No Partial Dependency

Partial Dependency: A proper subset of the candidate key
determines a non-prime attribute.
📚 Key Definitions
Prime Attribute: Any attribute that is part of at least one candidate key.
Non-Prime Attribute: Attribute NOT part of any candidate key.
Partial Dependency: Non-prime attribute determined by a proper subset of the candidate key (not the full key).

❌ Example of Partial Dependency

Customer Table with composite candidate key (Customer_ID, Store_ID):

Customer_ID 🔑Store_ID 🔑Location
C1S1Delhi
C2S1Delhi
C3S2Bangalore
C4S3Mumbai
C5S3Mumbai
❌ Partial Dependency Found!
Candidate Key = (Customer_ID, Store_ID)
Prime attrs = Customer_ID, Store_ID  |  Non-prime attr = Location

Notice: Store_ID=S1 always → Delhi; S2 always → Bangalore
So Store_ID → Location (only a part of the CK determines Location)
∴ This is a Partial Dependency → Table NOT in 2NF ❌
Figure 2: Partial Dependency — Store_ID (part of CK) determines Location (non-prime) ❌

✅ Convert to 2NF — Decompose!

1
Identify the partial dependency: Store_ID → Location
2
Separate it into a new table: Table 2 = (Store_ID, Location)
3
Keep remaining in original: Table 1 = (Customer_ID, Store_ID) — Store_ID stays as FK

📝 Condition to Check Partial Dependency (for GATE)

🔍 Checking for Partial Dependency
For each FD (LHS → RHS) in F: Check: Is LHS a PROPER SUBSET of any Candidate Key? AND Is RHS a Non-Prime Attribute? If BOTH TRUE → PARTIAL DEPENDENCY EXISTS → NOT in 2NF Note: If LHS == full CK → NOT partial (it's full functional dep) If RHS is prime attr → NOT partial (prime attrs are fine)

🧮 GATE Question Solved

📋 Given
R(A,B,C,D,E,F), F = {C→F, E→A, EC→D, A→B}
Find candidate key. Is the table in 2NF?
1
Find Candidate Key: RHS = {F,A,D,B}. Not in RHS → {E,C}. Take EC⁺ = {E,C,F,A,D,B} = All attrs. ∴ CK = EC
2
Prime Attrs: E, C  |  Non-Prime Attrs: A, B, D, F
3
Check C→F: Is C a proper subset of CK (EC)? ✅ Yes. Is F non-prime? ✅ Yes. → PARTIAL DEP!
Check E→A: Is E a proper subset of CK? ✅ Yes. Is A non-prime? ✅ Yes. → PARTIAL DEP!
4
Conclusion: Two partial dependencies exist → Table is NOT in 2NF ❌

🎯 GATE-Style PYQs — 2NF

Q1. A table has a composite key (A,B) and a FD B→C where C is non-prime. Is the table in 2NF?
👉 No. B is a proper subset of CK and C is non-prime → Partial dependency → NOT in 2NF.
Q2. If a table has a simple (single-attribute) candidate key, can it have a partial dependency?
👉 No. A proper subset of a single-attribute key is empty. No proper subset can determine anything → No partial dependency possible → Always in 2NF.
Q3. 2NF is violated only when the primary key is _______.
👉 Composite (multi-attribute). Simple keys can never have partial dependencies.

🟡 Third Normal Form (3NF)

RULES OF 3NF
Rule 1: Table must be in 2NF
Rule 2: No Transitive Dependency

Transitive Dependency: A Non-Prime attribute
is determined by another Non-Prime attribute.
🔗 What is Transitive Dependency?
If X → Y and Y → Z, then X → Z (by transitivity).
This becomes a problem when Y is a non-prime attribute determining Z (another non-prime attribute).

Think of it as: the non-key column is being controlled by another non-key column, not directly by the key.

❌ Example of Transitive Dependency

Student Table with Roll_No as PK:

Roll_No 🔑CityState
101MohaliPunjab
102MohaliPunjab
103MumbaiMaharashtra
❌ Transitive Dependency Found!
Roll_No → State ✅ (key determines non-prime — fine!)
State → City ❌ (non-prime determines another non-prime → TRANSITIVE DEP!)

So via transitivity: Roll_No → State → City
City is determined by State (a non-prime), not directly by Roll_No → NOT in 3NF
Figure 3: Transitive Dependency — State (non-prime) determines City (non-prime) ❌

📝 Direct Condition to Check 3NF (for GATE)

🔍 For Each FD (X → Y), Check:
Condition (OR — either one must be true): Option A: X is a Candidate Key or Super Key OR Option B: Y is a Prime Attribute If BOTH are FALSE for any FD → Transitive Dependency → NOT in 3NF ❌ If at least one is TRUE for ALL FDs → Table IS in 3NF ✅ Key difference from BCNF: BCNF has NO "Option B" — LHS must ALWAYS be CK

🧮 GATE Question Solved — R(A,B,C,D), F={AB→CD, D→A}

1
Find CKs: RHS = {C,D,A}. B not in RHS → B must be in CK. Take AB⁺ = {A,B,C,D} ✅ → CK1 = AB. A is in RHS of D→A, replace A with D: Take DB⁺ = {D,B,A,C,D} ✅ → CK2 = DB. CKs = {AB, DB}
2
Prime Attrs: A, B, D  |  Non-Prime: C only
3
AB→CD: LHS = AB = CK ✅ → Valid for 3NF
D→A: LHS = D ≠ CK (BD is CK, not D alone). Check RHS: A is prime ✅ → Valid for 3NF (Option B)
4
Conclusion: All FDs satisfy the 3NF condition → Table IS in 3NF ✅
⚠️ But is it in BCNF? → See the BCNF tab!
D→A fails BCNF because D is not a candidate key. 3NF and BCNF are different!

🎯 GATE-Style PYQs — 3NF

Q1. R(A,B,C), FDs: A→B, B→C. Is R in 3NF?
👉 CK = A. Prime = A, Non-prime = B, C. Check B→C: LHS (B) is not CK. RHS (C) is non-prime. BOTH FALSE → NOT in 3NF (transitive: A→B→C)
Q2. A table is in 3NF. Can it have a transitive dependency?
👉 No. 3NF by definition eliminates all transitive dependencies between non-prime attributes.
Q3. 3NF always ensures _______, but not always _______ (GATE 2016 concept).
👉 Dependency Preservation, but not always Lossless Decomposition. (Actually both are ensured — but BCNF only ensures lossless, not always dependency preservation!)

🟣 Boyce-Codd Normal Form (BCNF)

BCNF is called the Strict 3NF or Special Case of 3NF. It removes the "OR" condition that 3NF allows.

RULE OF BCNF (Stricter than 3NF)
For every FD (X → Y) in F: X must be a Candidate Key (or Super Key).

← That's it! No "OR RHS is prime" condition.
Every determinant must be a candidate key.
🔄 3NF vs BCNF — The Difference
3NF: LHS is CK  OR  RHS is prime attr
BCNF: LHS is CK  (always, no exception!)

Any FD that satisfies BCNF also satisfies 3NF. But NOT vice versa.
∴ Every BCNF relation is in 3NF, but every 3NF relation may NOT be in BCNF.

✅ BCNF Example — Student Table

Roll_NoNameVoter_IDAge
101VarunV00120
102RaviV00221
✅ Analysis
Candidate Keys: Roll_No and Voter_ID (both uniquely identify a student)
FDs: Roll_No→Name, Roll_No→Voter_ID, Voter_ID→Age, Voter_ID→Roll_No

Check each FD's LHS: Roll_No = CK ✅, Voter_ID = CK ✅
ALL LHS are CKs → Table IS in BCNF ✅

❌ BCNF Violation — R(A,B,C,D), F={AB→CD, D→A}

1
CKs = {AB, DB} (derived in 3NF tab)
2
AB→CD: LHS = AB = CK ✅ → Valid for BCNF
D→A: LHS = D. Is D a CK? No (BD is CK, D alone is not) ❌ → BCNF Violation!
3
Conclusion: Table is in 3NF ✅ but NOT in BCNF ❌

✅ Convert to BCNF — Decompose!

1
Problem FD: D→A. Compute D⁺ = {D, A}
2
Create R1 from D⁺: R1(D, A) with PK = D, FK = (none)
3
Remaining: Remove A from original, keep D: R2(B, C, D) with PK = BD (since BD was a CK)
Figure 4: BCNF Decomposition of R(A,B,C,D) → R1(D,A) + R2(B,C,D)

⭐ KEY POINT: 3NF vs BCNF — Decomposition Properties

🟡 3NF — Safe But Weaker
  • Always ensures Lossless Decomposition
  • Always ensures Dependency Preservation
  • May have minor redundancy (allows prime-attr FDs)
  • Used when dependency preservation is critical
🟣 BCNF — Strict But Risky
  • Always ensures Lossless Decomposition
  • NOT always Dependency Preserving
  • No redundancy (strictest allowed for practice)
  • Used when redundancy elimination is critical
🧪 Proof: BCNF is NOT always Dependency Preserving
From the example R(A,B,C,D) with FDs {AB→CD, D→A}:
After BCNF decomposition: R1(D,A) and R2(B,C,D)
• D→A ✅ preserved in R1
• AB→CD ❌ LOST — A is not in R2, so AB→CD cannot be checked within R2 alone.
∴ BCNF does NOT always preserve dependencies.

But 3NF would keep D→A (valid since A is prime) without decomposing, so all FDs stay intact.

🎯 GATE-Style PYQs — BCNF

Q1 (GATE 2019). Which of the following is true about BCNF?
👉 BCNF ensures lossless decomposition but NOT always dependency preservation. Every BCNF relation is in 3NF but not vice versa.
Q2 (GATE 2016). R(A,B,C,D), FDs={AB→CD, D→A}. Which NF is R in?
👉 CKs = AB, DB. Prime = A,B,D. Non-prime = C. AB→CD: LHS=CK ✅. D→A: LHS not CK ❌ for BCNF, but RHS (A) is prime ✅ for 3NF. → R is in 3NF but NOT in BCNF.
Q3. A table in BCNF is always in ___.
👉 3NF, 2NF, and 1NF (since BCNF is the strictest, it satisfies all weaker NFs).
Q4. 3NF always ensures dependency preservation but BCNF does not. True or False?
👉 TRUE. This is a classic GATE statement. 3NF synthesis algorithm always produces a dependency-preserving, lossless decomposition.
Q5 (GATE 2015). For BCNF decomposition, what must be true about common attributes between decomposed relations?
👉 The common attribute(s) must be a candidate key in at least one of the decomposed relations to guarantee lossless join.
