Weak Entity Set (दुर्बल एंटिटी सेट)

Master Weak Entity Sets, Owner (Strong) Entities, Identifying Relationships, Discriminators (Partial Keys), Total Participation requirements, and the 2-Table Relational Conversion Rule.

💡 1. What is a Weak Entity Set?

A Weak Entity Set is an entity set that does NOT have a Primary Key (no sufficient key attributes to uniquely identify its records on its own).

🏢 Real-Life Corporate Example: Employees & Dependents
Suppose an IT company (e.g. Infosys) maintains employee database records:
  • Strong Owner Entity (EMPLOYEE): Contains Emp_ID (Primary Key), Emp_Name, Salary. Employees deal directly with the company.
  • Weak Entity Set (DEPENDENT): Stores employee family members (e.g. Spouse Name, Age). Dependents do NOT deal with Infosys directly; they are identified only through the employee.
Existence Dependency: If Employee E1 leaves the company, Infosys automatically deletes all dependent records associated with E1 because the company has no independent relationship with dependents!

🧩 2. Core Components & ER Diagram Notations

  • 1. Weak Entity Set: An entity set that has NO primary key of its own.
    ER Symbol: (Double Rectangle)
  • 2. Strong Owner Entity Set: The primary key-holding entity upon which the weak entity depends.
    ER Symbol: (Single Rectangle)
  • 3. Identifying Relationship: Connects a weak entity set to its strong owner entity.
    ER Symbol: (Double Diamond)
  • 4. Total Participation (Existence Dependency): Weak entity MUST ALWAYS participate totally — it cannot exist without its owner.
    ER Symbol: (Double Line connecting Weak Entity to Identifying Relationship)
  • 5. Discriminator / Partial Key: Attribute that distinguishes weak entities within the same owner. (e.g. Dep_Name)
    ER Symbol: (Dashed Underline inside Dashed Ellipse)

⚡ 3. Relational Table Mapping Rules (Exam Favorite ⭐)

When converting a Weak Entity Set structure (Strong Entity + Identifying Relationship + Weak Entity) into RDBMS Relational Tables, follow these strict rules:

Rule 1: Number of Relational Tables Created

🔑 Table Reduction Formula (2 Tables Only!)
A Weak Entity Set and its Identifying Relationship are ALWAYS merged together into a single table!

Therefore, a Weak Entity structure requires EXACTLY 2 TABLES:
  1. Table 1 (Strong Entity Table): EMPLOYEE (Emp_ID [PK], E_Name, E_Salary).
  2. Table 2 (Merged Weak Entity Table): DEPENDENT (Emp_ID [FK], Dep_Name [Partial Key], Dep_Age).

Rule 2: Primary Key of the Weak Entity Table

Because `Dep_Name` can repeat across different employees (two employees can both have a child named "Rahul"), `Dep_Name` alone cannot be a Primary Key.

  • The Primary Key of the Weak Entity Table is a Composite Primary Key formed by combining:
    Primary Key of Owner Entity (Emp_ID) + Partial Key of Weak Entity (Dep_Name)
  • Composite Primary Key: (Emp_ID, Dep_Name).

🔑 Why is the Composite PK (Emp_ID, Dep_Name)?
Emp_ID alone as PK? Dep_Name alone as PK? Composite (Emp_ID, Dep_Name)?
❌ E1 repeats twice (E1→A and E1→B) → Not unique! ❌ "A" repeats for E1 and E2 → Not unique! ✅ (E1,A), (E1,B), (E2,A) → All unique! ✓

🎯 GATE, UGC-NET & IBPS SO IT Officer — Exam Focus PYQs

Q1: How is a Weak Entity Set represented in an ER Diagram?
👉 Answer: Double Rectangle [[ Weak Entity ]].

Q2: How is an Identifying Relationship represented in an ER Diagram?
👉 Answer: Double Diamond << Identifying Relationship >>.

Q3: How is a Discriminator / Partial Key represented in an ER Diagram?
👉 Answer: Dotted / Dashed Underline inside an Ellipse.

Q4: What is the Primary Key of a Weak Entity table in an RDBMS?
👉 Answer: Composite Primary Key = (Primary Key of Owner Entity + Partial Key of Weak Entity).

Q5: What is the MINIMUM number of tables required to convert a Strong Entity, Weak Entity, and Identifying Relationship into RDBMS?
👉 Answer: 2 Tables (The Identifying Relationship table is always merged into the Weak Entity table).
