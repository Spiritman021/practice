Software Engineering Basics
Definition, characteristics & origin of software engineering
Software Engineering = systematic, disciplined approach to developing, operating, testing & maintaining software using engineering principles to deliver high-quality software on time and within budget.
Software Characteristics
  • Developed / engineered — not manufactured like hardware.
  • Does not physically wear out (no bath-tub failure curve).
  • Maintenance is a major and costly part of its lifecycle.
  • Complexity increases as features increase.
  • Custom-built — cannot simply reuse physical components.
Software Crisis (Historical Problem)
⚠ Problems Faced
  • Late delivery & cost overruns
  • Poor quality software
  • Difficult to maintain
  • Requirement mismatch
  • Increasing complexity
✓ Solution

Software Engineering introduced as a discipline to bring engineering rigor — planning, processes, metrics, and quality assurance — to software development.

Software Process Models HIGH YIELD
Waterfall · Prototype · Spiral · Incremental · Iterative · V-Model · Agile
A. Waterfall Model — Sequential
Requirements→Design→Implementation→Testing→Deployment→Maintenance
✓ Advantages
  • Simple & easy to understand
  • Well-defined stages with clear milestones
  • Good documentation
  • Easy to manage (sequential phases)
✗ Disadvantages
  • Cannot accommodate changing requirements
  • Testing happens very late
  • Working software delivered late
  • High risk for complex projects
💡 Best Suited For
Stable, well-understood requirements. Small projects with clear scope.
B. Prototype Model — Clarify Requirements
Requirements→Build Prototype→Customer Feedback→Refine→Final System
  • Throwaway prototype — discarded after learning requirements.
  • Evolutionary prototype — gradually becomes the final system.
  • Used when customer does not know exactly what they want.
C. Spiral Model — Risk-Driven
🔑 Key Point
Spiral = Risk-driven model. Combination of iterative development + risk analysis. Best for large, complex, high-risk projects.
Each Spiral Loop
Planning→Risk Analysis→Engineering→Evaluation
D. Incremental Model — Deliver in Parts
  • Software developed & delivered in small increments.
  • v1 → Login  |  v2 → Profile  |  v3 → Payment
  • Advantage: Working software delivered early to users.
E. Iterative Model — Refine with Each Cycle
🔑 Key Difference
Incremental → adds new functionality in each iteration.
Iterative → improves / refines existing functionality in each cycle.
F. V-Model — Verification + Validation
Requirements ↘                        ↗Acceptance Testing
  System Design ↘                ↗System Testing
   Architecture ↘        ↗Integration Testing
    Module Design ↘ ↗Unit Testing
⬇    CODING    ⬇
  • Extension of Waterfall — each dev phase has a corresponding test phase.
  • Testing is planned early (alongside development).
  • V-Model = Verification + Validation
G. Agile Model — Flexible & Iterative
🔑 Key Focus Areas
Agile focuses on: Customer collaboration, working software, frequent delivery, responding to change, and iterative development.

Requirement Engineering
Functional vs Non-Functional Requirements
Requirement Engineering Activities
Feasibility Study→Elicitation→Analysis→Specification→Validation→Management
📋 Functional Requirements

WHAT the system should do.

  • Login & authentication
  • Search functionality
  • Generate report
  • Process payment
  • Reset password
📊 Non-Functional Requirements

HOW WELL the system should work.

  • Performance
  • Security
  • Reliability & Availability
  • Scalability
  • Usability & Portability
🧠 Easy Trick
Functional = WHAT?  |  Non-Functional = HOW WELL?

SRS — Software Requirements Specification HIGH YIELD
Document that captures all requirements — characteristics & scope
SRS is a formal document describing WHAT the system should do, not the detailed HOW. It serves as a contract between client and development team.
Good SRS Characteristics — C C U V C M T
  • Correct — accurately reflects requirements
  • Complete — covers all requirements
  • Unambiguous — one interpretation only
  • Verifiable — can be tested
  • Consistent — no contradictions
  • Modifiable — easy to update
  • Traceable — linked to source
⚠ Important
SRS describes WHAT — not detailed HOW. The HOW is covered in the Design phase.

Cohesion & Coupling TOP PRIORITY 🔥🔥
Measure of module quality — extremely important for exams
Cohesion — elements inside a module belonging together
✓ Golden Rule
High Cohesion = GOOD — all elements contribute to one specific task.

Types of Cohesion — Worst → Best:

WORST Coincidental→ Logical→ Temporal→ Procedural→ Communicational→ Sequential→ Functional BEST
Coupling — dependency between modules
✓ Golden Rule
Low Coupling = GOOD — modules should be as independent as possible.

Types of Coupling — Strongest/Worst → Weakest/Best:

WORST Content→ Common→ External→ Control→ Stamp→ Data BEST
🏆 Golden Design Rule
High Cohesion + Low Coupling = GOOD Design

LOC — Lines of Code
Simplest but language-dependent software size metric
  • Used to estimate size, productivity and effort. Productivity = LOC / person-month.
  • Limitation: LOC depends heavily on programming language and coding style.
  • KLOC = Kilo Lines of Code = 1,000 lines (used in COCOMO).
  • LOC can be misleading — more lines does not equal more value.

Function Point Analysis — FPA HIGH YIELD
Language-independent software size measurement based on functionality
FPA measures software size based on functionality provided to users — independent of programming language used.
ComponentFull FormDescription
EIExternal InputsData entered by users (forms, files)
EOExternal OutputsData output to users (reports, screens)
EQExternal QueriesInteractive input/output combinations
ILFInternal Logical FilesData files maintained within the system
EIFExternal Interface FilesFiles shared from external applications
FP = UFP × (0.65 + 0.01 × ΣFi) // UFP = Unadjusted Function Points (sum of all 5 components) // Fi = 14 value adjustment factors (each rated 0–5)

Software Testing TOP PRIORITY 🔥🔥
Verification vs Validation — the most important distinction
Testing = executing software with the intent of finding defects and verifying it meets requirements.
✔ Verification

“Are we building the product RIGHT?”

  • Static analysis, reviews, inspections
  • Walkthroughs & checklists
  • Done without executing code
✔ Validation

“Are we building the RIGHT product?”

  • Dynamic testing, actual execution
  • Ensures customer requirements met
  • Done by running the software

Black Box vs White Box Testing TOP PRIORITY 🔥🔥
The two fundamental testing approaches
⬛ Black Box Testing — WHAT

Tester does NOT know internal code

Techniques:
  • Equivalence Partitioning
  • Boundary Value Analysis
  • Decision Table Testing
  • State Transition Testing
  • Cause-Effect Graphing
⬜ White Box Testing — HOW

Tester KNOWS internal implementation

Techniques:
  • Statement Coverage
  • Branch / Decision Coverage
  • Path Coverage
  • Condition Coverage
  • Basis Path Testing (Cyclomatic)
🧠 Easy Trick
Black Box → WHAT (no code knowledge)  |  White Box → HOW (code knowledge needed)

Equivalence Partitioning
Divide inputs into groups where each group behaves identically
Group inputs into equivalence classes where all values behave identically. Test one representative value from each class instead of every value.
📘 Example — Age field: 18–60 years allowed
< 18 → Invalid18–60 → Valid> 60 → Invalid

Test representatives: 10, 35, 75 instead of every single value.

19
Boundary Value Analysis — BVA HIGH YIELD
Test values at and around the boundaries of input ranges
Test values exactly at, just below, and just above the boundary — because bugs most frequently occur at boundaries.
📘 Example — Age: 18–60 years
171819…596061

Test: 17, 18, 19, 59, 60, 61 (min−1, min, min+1, max−1, max, max+1)

Regression Testing HIGH YIELD
Ensure new changes do not break existing functionality
After modifying or fixing software, re-run existing test cases to ensure changes have not broken any previously working functionality.
Code Change / Bug Fix→Re-run Old Test Cases→Verify No Regression
💡 Remember
Regression Testing = “Check old functionality after new changes”. Highly automated in CI/CD pipelines.
21
Smoke Testing & Sanity Testing
Quick build health checks before deeper testing
🔥 Smoke Testing

“Is this build alive enough to test?”

  • Broad & shallow — covers all major features quickly
  • Tests basic build stability
  • Done before detailed testing begins
  • If smoke fails → build rejected
🧪 Sanity Testing

“Does this specific fix/change work?”

  • Narrow & deep — focuses on specific changed area
  • Validates a specific bug fix or feature
  • Subset of regression testing
  • Usually unscripted / quick
🧠 Key Difference
Smoke → broad + shallow (whole build)  |  Sanity → narrow + deep (specific change)

Alpha & Beta Testing
User acceptance testing — internal vs external
🏢 Alpha Testing
  • Performed at developer's organization
  • Done by internal users / QA team
  • Simulated / real environment
  • Done before beta testing
  • Developer monitors & records errors
🌎 Beta Testing
  • Performed at client's site
  • Done by real end users
  • Real environment, no developer monitoring
  • Users report bugs directly
  • Last phase before public release
🧠 Easy Memory
Alpha → Internal (developer's site)  |  Beta → External (real users)

Defect / Bug Life Cycle
States a defect passes through from discovery to closure
Bug Life Cycle States
New→Assigned→Open→Fixed→Retest→Verified→Closed
⚠ If Fix Fails
After “Retest” — if fix did not work → Bug status becomes “Reopened” → goes back to “Assigned”.

Other statuses: Deferred (postponed), Rejected (not a real bug), Duplicate (already reported).

Software Quality & CMM Levels
Quality attributes and Capability Maturity Model
Key Quality Attributes
  • Correctness — does it do what it should?
  • Reliability — probability of performing without failure for a specified time/environment
  • Efficiency — optimal resource usage
  • Usability — ease of use
  • Maintainability — easy to modify
  • Portability — works across environments
  • Security — protected from threats
  • Scalability — handles growth

📌 ISO 9126 Quality Model
ISO 9126 defines six quality characteristics: Functionality, Reliability, Usability, Efficiency, Maintainability, Portability. It is the international standard for software product quality evaluation.

Software Configuration Management — SCM
Control and track changes to software artifacts
  • Version Control — track changes over time (Git, GitHub, GitLab)
  • Change Control — formal approval for changes
  • Configuration Identification — identify & label artifacts
  • Configuration Auditing — verify completeness & correctness
  • Status Accounting — record & report configuration status
📌 Baseline
A formally reviewed and approved version of a software artifact that serves as a reference point. Changes from baseline require formal change control.
