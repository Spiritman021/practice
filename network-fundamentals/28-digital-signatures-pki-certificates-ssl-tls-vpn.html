28.1 Digital Signatures Mechanics

A Digital Signature provides three security guarantees for network communications: Authentication (sender identity), Integrity (unaltered payload), and Non-Repudiation (sender cannot deny sending the message).

How Digital Signatures Work

  1. Signing (Sender): Sender computes a SHA-256 hash of the message, then encrypts the hash digest using their Private Key. The resulting string is the Digital Signature appended to the message.
  2. Verification (Receiver): Receiver decrypts the signature using the Sender's Public Key to get Hash A. Receiver independently computes Hash B of the received message body. If Hash A == Hash B, the signature is VALID!

Section 28.2

PKI & Digital Certificates (X.509)

Public Key Infrastructure (PKI) binds an identity (e.g. google.com) to a public key using a **Digital Certificate (X.509 standard)** issued by a trusted **Certificate Authority (CA)**.

Key X.509 Certificate Fields

  • Subject / Domain Name: Common Name (CN) and Subject Alternative Names (SAN).
  • Public Key: Public key of the website/owner.
  • Issuer: Certificate Authority (CA) that validated & issued the certificate.
  • Validity Period: Not Before & Not After timestamps.
  • CA Digital Signature: Signature computed by CA's private key to prevent tampering.

Section 28.3

Chain of Trust & Revocation (CRL/OCSP)

Web browsers verify certificates using a **Chain of Trust**:

Certificate LevelRole
Root CA CertificateSelf-signed certificate pre-installed into browser/OS trusted root store.
Intermediate CA CertificateIssued by Root CA to sign end-entity certificates (keeps Root CA offline for security).
Leaf / Server CertificateIssued to end domain (e.g. example.com).

Certificate Revocation Checking

  • CRL (Certificate Revocation List): CA publishes a downloadable list of revoked certificate serial numbers.
  • OCSP (Online Certificate Status Protocol): Real-time HTTP query asking CA server if a specific certificate is still valid.

28.4 SSL/TLS 1.3 Handshake Protocol

TLS 1.3 (RFC 8446) completes key negotiation in a single round-trip time (**1-RTT**):

  1. ClientHello: Client sends supported cipher suites, random number, and key share parameters (ECDHE).
  2. ServerHello: Server selects cipher suite, sends server key share, X.509 certificate, and digital signature.
  3. Symmetric Key Calculation: Both sides generate the shared master secret key independently.
  4. Finished & Encrypted Traffic: Encrypted application data exchange begins!

Section 28.5

VPN Concepts & Architecture

A VPN (Virtual Private Network) creates an encrypted, secure tunnel over a public untrusted network (the Internet).

User to Office
Remote Access VPN
Individual user running VPN software (e.g. OpenVPN client) connects securely to company network.
Branch to HQ
Site-to-Site VPN
VPN routers at branch offices connect permanently to HQ VPN gateway over an IPsec tunnel.

Section 28.6

IPsec Suite (AH vs ESP, Tunnel vs Transport)

IPsec (IP Security) is a framework of protocols at the Network Layer (Layer 3) that provides end-to-end security.

1. IPsec Protocols: AH vs ESP

  • AH (Authentication Header - IP Protocol 51): Provides data integrity and authentication. **Does NOT provide encryption / confidentiality!**
  • ESP (Encapsulating Security Payload - IP Protocol 50): Provides confidentiality (encryption), authentication, and integrity. (Industry standard!).

2. IPsec Modes: Transport vs Tunnel

ModeHeader EncapsulationPrimary Usage
Transport ModeEncrypts ONLY the IP payload (original IP header stays intact).Host-to-Host communication.
Tunnel ModeEncrypts the ENTIRE original IP packet (adds new outer IP header).Gateway-to-Gateway / Site-to-Site VPNs.
